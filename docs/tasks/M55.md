## 背景

会話ペインは、行を選択した時点の会話を表示し、その後に送った発話と Claude の返答は、別の行を選択して戻るまで表示しない
(`No conversation to show` を表示している間の Refresh を除く)。Settings ウィンドウは、グループのフォームである。
ライトの一覧の地は、行の枠の白に近く、ダークの見出しの帯は、行の枠に近い。発言ごとのコピーの反応は、アイコンの形の変化だけである。
Setup Check は、⌄ メニューから開く独立したウィンドウである。色は赤の 1 つで、未確認だけを示し、waiting には色が無い。
これらを、DESIGN.md の仕様に合わせて変更する。
ほかに、システムがアプリのプロセスの中に表示するパネルを、ログで特定できるようにする(記録の追加だけで、動作は変更しない)。

タスクは、CLI(T1)、アプリ(T2〜T8、T10、T11)、スクリプトと画像(T9)に分かれる。T1 は、アプリのタスクより先に実装する(T2 が `updated_at` を使用する)。
T4、T5、T6 は、互いに独立である。T7〜T10 は、T4 の後に実装する(T10 は、T4 と同じメニューとウィンドウの処理を変更する)。T7、T8、T9 は、互いに独立である。T11 は、ほかのタスクと独立である。

### T2(アプリ・Core): 会話ペインの再読み込みの契機と手順

- DESIGN.md §4.6「会話ペインの再読み込み」の、契機 1〜3 と手順を実装する
- 契機 1 の判定は、Core に配置する(テストできる純粋な処理にする): daemon から受け取った一覧の更新の前後で、
  会話ペインが表示している Running の行のセッションの `status` が変化したか。`unreviewed` だけの変化、ほかの項目だけの変化、
  行の追加と削除は、契機にしない。「ポップオーバーとウィンドウのどちらも表示していない間は、契機にしない」の条件は、
  `MainSurfaceModel`(表示している面を保持している層)で適用する。Core の判定は、面の表示の状態を参照しない
- 契機 1 は、`conversations index` を実行して、終了の後に `conversations show` を実行する。index の exit code に関係なく、show を実行する。
  プロセスの起動は、既存の注入の仕組み(テストでは実際のプロセスを起動しない)を使用する
- 契機 1 の index は、ポップオーバーまたはウィンドウを開いたときの index(`runIndexThenSearch` の `indexProcess`)とは別のプロセスの枠で実行する。
  互いに中止しない。この index の進捗(`Indexing N of M…`)、全構築の状態(`fullBuildChanged`)、エラー終了(`indexFailed`、`historyFetchFailed`)は、
  表示せず、一覧の状態を変更しない(出力は読み捨ててよい。`--json` を指定する必要は無い)
- 契機 1 の後の再読み込み: 契機 1 の再読み込みの完了から §9 の時間(2 秒)の後に、同じ手順(index、show)で、もう 1 回再読み込みする。
  この時間の間に、別の再読み込みが開始したとき、表示する会話が切り替わったとき、面を表示しなくなったときは、実行しない。
  この再読み込みの後には、もう 1 回の再読み込みを予約しない。契機 1 の再読み込みの実行中に次の契機が発生した場合と、契機 1 が再実行にまとめられた場合は、
  その再実行の完了の後に実行する。時間の待ちは、テストで時間を進められる注入の仕組みにする
- 契機 2 と契機 3 は、契機の後に最初に受け取った search の結果(成功または失敗)の後に、show を実行する
  (その契機の search が、後の契機の search に置き換えられた場合は、置き換えた search の結果を、その契機の結果として扱う。
  Refresh の `noteRefreshSearchFinished` と同じ考え方である)。契機 2 で、index がエラー終了して search を実行しないとき
  (`handleIndexFinished`)は、index の終了の後に show を実行する。
  契機 3 は、表示している会話の種類(Running、History、Archive の一覧)に関係なく実行する。
  `No conversation to show` を表示している間の Refresh で show を再度実行する既存の処理は、契機 3 に統合する
- 再読み込みの実行中(index または search の終了を待っている間を含む)に次の契機が発生したときは、完了の後に 1 回だけ再度実行する。
  この再実行は、契機の種類に関係なく、契機 1 の手順(index、show の順)で実行する。会話の最初の読み込みの実行中に発生した契機は、
  最初の読み込みの完了の後に実行する(最初の読み込みを中止しない)。表示する会話が切り替わったときは、結果を破棄する。
  `session_id` が空の行では、実行しない
- 会話の最初の読み込み(`loadConversation`): Running の行の会話では、index を実行して、終了の後に(exit code に関係なく)show を実行する
  (契機 1 の index と同じ枠と扱い)。History の行と、Archive の一覧の行の会話では、show だけを実行する(DESIGN.md §4.6「会話ペインの表示」)
- 再読み込みの間、表示中の内容、ヒット、エラーの表示を消去しない(最初の読み込みは、既存の最初の読み込みと同じく、表示を消去してから読み込む)
- show が失敗したとき(exit 1、exit 2、出力を解釈できない)は、表示中の内容を維持し、エラーを新しく表示しない
- ヒットの現在位置の規則(DESIGN.md §4.6「会話ペインの再読み込み」の「ヒット」)を実装する
- `ConversationDetail` に `updated_at` を追加する(フィールドが無い出力も解釈できるようにし、その場合は、search の結果の値を使用する)。
  終端マーカーの経過時間は、最初の読み込みと再読み込みの両方で、show の `updated_at` から求める
- 既存実装: `MainSurfaceModel.swift`(`loadConversation`、`handleShowResult`、`refresh`、`noteRefreshSearchFinished`、`agentsUpdated`、search の完了の処理)、
  `ShiibarCcCore/ConversationsWire.swift`、`UnifiedListState.swift`
- 完了報告に記載すること: 発話の送信(status が working になる時点)と、応答の完了(status が idle になる時点)のそれぞれで、
  transcript に、その発話と返答が書き込まれているかどうかは、この指示書では確認していない(契機 1 の後の再読み込みは、このために実行する)。
  実装とテストは、仕様のとおりにする。
  実装の中で、この前提を確認できる材料(`fixtures/` の記録など)を見つけた場合は、内容を報告する

### T3(アプリ・WebPaneKit): 会話ペインの表示の更新

- DESIGN.md §4.6「会話ペインの再読み込み」の「結果の反映」と「スクロール」を、会話ペインのページ(`ConversationsWebPaneKit`)に実装する
- ページに、表示の更新の入口を追加する(既存の `load` は、最初の読み込みのままにする)。更新は、次の 3 つの場合を区別する:
  発言の列が同じ(`seq`、`role`、`text` がすべて一致する。終端マーカーの経過時間だけを更新する)、末尾に発言が追加されただけ(追加された発言の要素だけを追加し、既存の要素、
  選択範囲、展開の状態、コピーの反応を維持する)、表示中の発言が変化した(全体を描画し直す)。
  どの場合かの判定は、Swift 側で実行して、結果をページに渡す(意味の判定をページで実行しない — DESIGN.md §4.6「描画エンジン」)
- スクロール: 表示を更新する直前(更新の結果をページに適用する時点。契機の時点ではない)に、終端マーカーの一部が表示範囲にあったかどうかを、ページで判定する。あった場合は、更新の後に下端までスクロールする。
  無かった場合は、スクロール位置を変更しない(全体を描画し直した場合は、表示範囲の先頭にあった発言を同じ位置に表示し、その発言が無い場合は下端までスクロールする)。
  発言の列が表示中と同じ場合は、終端マーカーの位置に関係なく、スクロール位置を変更しない
- 更新の後に、ミニマップ、ヒットのハイライト、展開のボタンの件数バッジを、更新した内容で再計算する
- 配信の世代の確認(描画の完了の通知と再配信)は、更新にも適用する
- 既存実装: `PageTemplate.swift`(`shiibarAPI.load`、`render`、`setHits`、スクロールの記憶)、`WebPane.swift`(`load`、`setHits`)

### T8(アプリ): トレイアイコンの点

- DESIGN.md §4.5「見た目の正」と menubar-design.html のとおりに、トレイアイコンの点を実装する: waiting が 1 台以上でオレンジ、
  waiting が無くて unreviewed が 1 台以上でアクセントカラー、どちらも無ければ点なし(テンプレート画像)
- 点の種類(なし、オレンジ、アクセントカラー)の判定は、Core に配置する
- 点の色は、メニューバーのボタンの外観で解決した `systemOrange` と `controlAccentColor` である。位置、大きさ、明色のフチ、減光は、変更の前の点と同じにする。
  色は、画像を作成する前に、ボタンの `effectiveAppearance` で具体的な sRGB の値に解決し(`performAsCurrentDrawingAppearance`)、その値を描画と比較の両方に使用する
  (画像の描画の処理は、描画の時点の外観で実行されるので、その中で動的な色を解決しない)。Core の比較には、RGBA の数値を渡す
- 「画像を設定するのは、表示する内容が変化したときだけ」の規則(DESIGN.md §4.5、§8.51)を維持する。比較する内容に、点の種類と、解決した色の値を含める。
  同じ内容の画像を、繰り返して設定しない
- アクセントカラーの設定の変更(`NSColor.systemColorsDidChangeNotification`)で、点の色が変化した場合に、画像を設定し直す。通知の内容と発生の条件は、
  開発環境の SDK の文書で確認し、確認した方法を完了報告に記載する
- daemon の切断中も、最後に受け取った一覧で点の種類を判定し、減光して表示する(変更の前の未確認の点と同じ)。エージェントなしの表示は、変更しない
- 既存実装: `TrayIconRenderer.swift`、`ShiibarCcCore` の `TrayImageGate.swift`(比較)と `Rollup.swift`(点の判定)、トレイアイコンを更新する処理(`AppState.swift`)
