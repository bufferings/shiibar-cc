## 背景

この指示書の実装の前の動作は、次のとおりである。daemon が追跡するのは、対応ターミナル(iTerm2 と Terminal.app)のセッションだけである。それ以外のターミナルのセッションは、hook の報告を
CLI が破棄し、reconcile も送らないので、Running に表示されず、通知も発生しない。Resume と Branch を開くターミナルは、最新のエントリの
ターミナルを観測して決める。未確認は、Jump の成功(と `Mark all as read`)でだけ下りる。
これらを、DESIGN.md の仕様に合わせて変更する:

1. 対応ターミナルの target を導出できない、ターミナルで実行しているセッションを、`process:<pid>` の target で追跡する(ジャンプだけができない)。
   鍵は、そのセッションを実行している `claude` のプロセスの pid である。ターミナルを持たないセッションは追跡しない
2. Ghostty(1.4.0 以上)を、3 つ目の対応ターミナルにする(target は `ghostty:<tty パス>`)
3. Resume と Branch を開くターミナルを、Settings の `Terminal` で選択する(観測による決定を廃止する)
4. 利用者が選択した Running の行の選択が 1 秒続いた時点で、未確認を下ろす(すべてのセッションで同じ規則)。グローバルホットキーで開いたときに、先頭の行を選択しない
5. 実行中のセッションが起動した別の `claude` のプロセス(Bash ツールからの `claude -p` など)の report を、親のエントリに適用しない
   (pid が同じで `session_id` が異なる report を無視する。対応ターミナルの target にも適用する)

**§3.4 の遷移の表は、行を追加せず、既存の行の遷移も変更しない**。表の前文(追跡する対象、表を適用するエントリの決め方、入れ子のセッションの report を表の適用の前に無視すること)と、seen の行の「送る側」の説明は、§3.4 を参照する(seen の遷移は同じ)。表の「未登録」の列と状態の列は、§3.6「pid による統合」の「hook の report」で、適用するエントリを決め、§3.6「入れ子のセッション」で無視しないと判定した後の状態で読む。テーブル駆動テストは、既存の期待値を変更せずに、target が `process:` と `ghostty:` の場合を加える(同じ遷移になること)。

タスクは、実機での確認(S1〜S5)、proto と CLI と daemon と client(T1〜T6、T14、T16)、アプリ(T7〜T11、T17)、そのほか(T12、T13、T15)に分かれる。

## 実機での確認(スパイク)

### 確認済みの内容(2026-11-21。Ghostty 1.4.0 / iTerm2 3.7.6 / Claude Code 2.1.330 / macOS 27.2.1)

結果は、DESIGN.md §7-8、§7-9、§7-10、§7-12 に記録している。実装は、次の内容を前提にする。

- **S1(Ghostty の鍵と走査)**: hook の祖先 walk で取る tty と pid は、AppleScript の `tty of terminal` と `pid of terminal`、`claude agents --json` の pid と一致する。
  親連鎖は、hook の sh → claude → シェル → login → ghostty である。ウィンドウ、タブ、分割の端末は、それぞれ別の `terminal` と `tty` を返す。
  `terminal` を 1 つずつ取り出す列挙は、列挙の途中で端末が閉じられると、エラー -1719 になる。`tty of every terminal` の形の、1 回の照会での取得は動作する。
  `v1.3.0` と `v1.3.1` の辞書の `terminal` には `tty` が無く、`application` の `version` はある(ソースで確認)。
  リリースではないビルドのバージョンは、`X.Y.Z-<ブランチ名>+<短いハッシュ>` の形式である(ソースで確認)
- **S2(Ghostty の focus と、ウィンドウを開く操作)**: `every terminal whose tty is "<tty パス>"` で端末を特定できる。`focus` だけで、別のウィンドウ、
  同じウィンドウの別のタブ、同じタブの別の分割の端末が、前面のウィンドウの `focused terminal` になる(`activate window` と `select tab` は不要)。
  tty が一致しない場合は 0 件で、何も動かない。前面の端末は `tty of focused terminal of selected tab of front window` で取得できる。
  surface configuration の `initial input` に、コマンドと末尾の改行を指定すると、`new window` と `new tab` の対話シェルで実行される
  (`claude` は、rc を通った PATH で解決される)。`input text` は貼り付けの扱いで、改行を含めても実行されない。
  空白、`'`、`"` を含む cwd は、シェルの単一引用符のエスケープと、AppleScript の文字列のエスケープの組み合わせで動作する。
  AppleScript を無効にする設定は `macos-applescript`(既定は true。ソースで確認)。
  ghostty モジュールが生成する形のスクリプト(バージョンの照会、`tty of every terminal` の走査、`activate` の後の `new window with configuration`)は、
  実物の Ghostty 1.4.0 で動作する。`application` の `frontmost` は、辞書にある
- **インストールされていないアプリを対象にしたスクリプト**(DESIGN.md §7-10): `application id "<バンドル ID>"` を含むスクリプトは、そのアプリがインストールされていない場合、
  `is running` の条件や `try` の中にあっても、実行の前にエラー(-1728)になる。`application "<名前>" is running` は false を返す。
  アプリの固有の用語を `tell` の中で使用するスクリプトは、そのアプリがインストールされていない場合、名前で指定しても、実行の前にエラー(-2741)になる
  (同じスクリプトの中の is-running の確認は、実行されない)。インストールされていない別の名前とバンドル ID で確認した
- **S3(祖先 walk の pid と、入れ子のセッション)**: iTerm2 と Ghostty で、hook の sh は制御端末を持たず、walk は `claude` に到達する(2〜3 段)。
  その pid は、`claude agents --json` の pid と一致する。実行中のセッションの Bash ツールから実行した `claude -p` の hook は、子の `claude` も制御端末を持たないので、
  親の `claude` の pid と tty を取る(5 段程度。`ITERM_SESSION_ID` も相続する)。子の `session_id` は、親と異なる。
  切り離して起動した `claude -p` の report は、drop される。ターミナルのシェルから実行した `claude -p` は、自分の制御端末を持ち、
  `claude agents --json` の一覧に `kind` が `interactive` で含まれる(一覧では、対話のセッションと判別できない)
- **S4(hook の実行時間。変更の前の値)**: `shiibar-cc report PostToolUse` の 60 回の実行で、中央値は、iTerm2(祖先 walk なし)が 3.1 ms、
  Terminal.app(祖先 walk あり)が 3.7 ms、対応ターミナル以外(破棄)が 3.0 ms である。daemon の有無による差は無い(DESIGN.md §8.66)
- **S4(hook の実行時間。変更の後の値)**: リリースビルドを、同じ方法で計測した。中央値は、iTerm2 が 3.7 ms、Terminal.app が 3.6 ms、
  対応ターミナル以外(`process:` として送信)が 3.7 ms で、最大は 6.0 ms である(daemon が起動している場合。DESIGN.md §7-9 の表)。
  判定は、この表の値で行い、基準(1 回の実行が 100 ミリ秒以下で、変更の前の 2 倍以下)を満たす。ビルドの直後の、バイナリの最初の 1 回の実行(233 ms)は、判定の対象に含めない
- **Terminal.app の、`id` もタブも読み取れないウィンドウ**(DESIGN.md §7-7): Terminal.app は、ターミナルのウィンドウをすべて閉じた後も起動している間、
  `count of windows` が 1 で、`id of w` と `tabs of w` がエラーになるウィンドウのオブジェクトを保持する場合がある。T14 の走査と `focused` のスクリプトを、
  この状態の Terminal.app で実行し、走査が失敗 0 件で完了すること、`focused` が「なし」を返すことを確認した
- **ターミナルのウィンドウを閉じたときの SessionEnd**(DESIGN.md §7-12。Terminal.app 488.9 / Ghostty 1.4.0 / iTerm2 3.7.6): ウィンドウを閉じると、約 3.5〜5.5 秒後に SessionEnd の hook が実行される。
  その時点で、`claude` のプロセスも祖先も、制御端末を持たない(環境変数は残っている)。閉じてから hook までの間は、`claude` は tty を持ったまま動作していて、
  この間の完全な reconcile は、エントリを `process:<pid>` に付け替える。
  T16 のビルドで、ウィンドウを閉じてから、daemon の一覧からエントリが無くなるまでの時間を計測した: Terminal.app が 3.6 秒、Ghostty が 5.4 秒、iTerm2 が 5.4 秒
  (iTerm2 の、タブを閉じる操作も 5.4 秒)。閉じた直後に reconcile を実行した場合(iTerm2)は、エントリが `process:<pid>` に付け替わった後、5.6 秒の時点で無くなる。
  Terminal.app と Ghostty の、タブだけを閉じる操作、分割のペインだけを閉じる操作、画面の操作でウィンドウを閉じた場合、
  Terminal.app の、閉じる前に確認のダイアログを表示する設定は、確認していない(実機スモーク 4)
- **認証コードの AutoFill のメニュー**(DESIGN.md §7-11): Apple の公式の文書で、`Info.plist` の `NSAutoFillRequiresTextContentTypeForOneTimeCodeOnMac` の動作を確認した。
  検索欄の位置に表示されるウィンドウ(クラスの名前は `SPRoundedWindow`)は、このキーだけでは止まらない(2026-11-21 に実機で確認)。
  UserDefaults の `NSAutoFillHeuristicControllerEnabled`(公式の文書に記載が無い)を false にした場合に表示されなくなることは、未確認である(実機スモーク 20)

### T1(proto・CLI): target の生成規則と、report の `pid`

- 仕様: DESIGN.md §4.1「target の生成規則」・§2・§4.2 の report の `pid`
- すべての report で、最初に祖先 walk を実行し、制御端末を持つ最初の祖先の pid と tty を取る。上限(§9)まで見つからなければ、report を drop する
  (`TERM_PROGRAM` が `iTerm.app` の場合も同じである)
- `derive_target` を、3 つの対応ターミナルの分岐と、`process:<pid>` の分岐にする。report に `pid` を加える(任意の項目)
- Ghostty の分岐: `TERM_PROGRAM` が `ghostty` で、`TERM_PROGRAM_VERSION` が 1.4.0 以上のときだけ `ghostty:<tty パス>` にする。
  バージョンは、最初の `-` または `+` より前の部分を、`major.minor.patch` の数値の組として比較する(リリースではないビルドの値は `1.4.0-main+abc1234` の形式である)。
  無い、解釈できない、1.4.0 未満のときは `process:<pid>` にする
- `TERM_PROGRAM` が `iTerm.app` で、`ITERM_SESSION_ID` が無い、空、`:` を含まない、のいずれかの場合は、`process:<pid>` にする(drop しない)
- walk は、`shiibar-cc report` のプロセス自身から開始する
- hook を阻害しない規則(常に exit 0、タイムアウト 1 秒 — §4.1)は、変更しない
- 既存実装: `crates/shiibar-cc-proto/src/extract.rs`(`derive_target`、`build_report`、`controlling_process_from_ancestor_walk`)、
  `crates/shiibar-cc/src/report_cmd.rs`(環境変数の読み取り、祖先 walk を実行する条件、drop の箇所)、`crates/shiibar-cc-proto/src/lib.rs`(`ReportPayload`)

### T2(daemon): エントリの `pid`、pid による統合、`rekey`、入れ子のセッション

- 仕様: DESIGN.md §3.6(属性の `pid`、「`process:` のエントリ」「pid による統合」「入れ子のセッション」)・§3.5 の prune と更新専用・§4.2
- 原則: **エントリの target を決めるのは、走査が完全な回の reconcile である。hook の report は、エントリの target を変更しない**
- エントリに `pid` を加える(適用するたびに上書きする。受け取った内容に `pid` が無い場合は、エントリの `pid` を変更しない)。**`state.json` には保存しない**(起動の直後は、どのエントリも不明である)。一覧と購読の応答には含めない
- hook の report(target T、pid P): 適用するエントリを、(a) target が T のエントリ、(b) 無ければ、pid が P と同じエントリ(target は変更しない)、
  (c) どちらも無ければ未登録、の順で決める。決めたエントリに §3.4 の遷移を適用し、`pid` を P にする。SessionEnd も、同じ順で決めたエントリだけを削除する(reason `session_end`)
- 入れ子のセッション: (a) または (b) でエントリを決めた report は、遷移を適用する前に、次の順で判定する。(1) report の `session_id` がエントリの `session_id` と同じなら、適用する。
  (2) 異なる場合で、report に `pid` が無い、エントリの `pid` が不明、または 2 つの `pid` が異なるときは、適用する。(3) `session_id` が異なり、`pid` が同じ場合は、
  SessionStart で `source` が `clear` または `resume` の report だけを適用し、それ以外の report は無視する(エントリを変更しない。`last_seen` と `last_report_at` も更新しない。
  SessionEnd でも削除しない。`state.json` への保存と配信も発生しない)。判定は、`transitions.rs` の遷移の前に置く(遷移の関数は変更しない)。
  判定そのものは、純関数にして、テストする
- 走査が完全な回の reconcile: (1) target が登録済みのエントリに一致するセッションを、すべて先に適用する(`pid` を上書きする)。
  (2) 残りのセッション(target T が未登録、pid P)を適用する — pid が P と同じで、target がこの回の live 集合に無いエントリ(複数ある場合は、その中で `last_seen` が最も新しいもの。同じ場合は `created_at` が新しいもの)があるときは、
  そのエントリの target を T に付け替えて、「既知」として適用する。該当するエントリが無いときは、「未追跡」として追加する。(3) prune を実行する。
  結果が、セッションの並びの順に依存しないこと(テストで、両方の順を確認する)
- 走査が不完全な回の更新専用のセッション(`update_only`): 適用するエントリを、hook の report の (a)、(b) と同じ順で決め、§3.5 の「既知」の規則をそのまま適用する
  (status、unreviewed、`message`、`since`、`last_seen`、`session_id`、`cwd`)。該当するエントリが無ければ、何も実行しない。エントリの作成、付け替え、prune は実行しない。更新専用のセッションの target は、`process:<pid>` である
- 走査が不完全な回の、更新専用でないセッション(成功した走査に一致したセッション。target T、pid P): target が T のエントリがあれば、「既知」として適用する。
  無くて、pid が P と同じエントリがあれば、そのエントリに「既知」を適用する(付け替えない。作成しない)。どちらも無ければ、「未追跡」として追加する。prune は実行しない
- 付け替え: エントリの `target` だけを変更し、ほかの属性をすべて引き継ぐ。配信は、`agent_removed`(古い target、reason `rekey`、`to`)と、その直後の、
  新しい target の `status_changed` である(差分が無くても配信する。1 回の reconcile の配信をまとめる実装でも、この 2 つを隣り合わせて、この順で送る。この `status_changed` は、付け替えの後の「既知」の適用を反映した内容で、
  そのセッションについて、その回に配信する唯一の `status_changed` である)
- 統合で、エントリを削除しない。pid が同じエントリが、2 つの対応ターミナルの target で登録されている場合も、統合しない(走査に無い側は、prune が削除する)
- pid が同じエントリが複数ある場合は、`last_seen` が最も新しいエントリを対象にする(同じ場合は、`created_at` が新しいエントリ)。受け取った内容の `pid` が無い場合と、エントリの `pid` が不明の場合は、target だけで突き合わせる
- prune は、その回のセッションをすべて適用し、付け替えを終えた後のエントリで、target が live 集合に無いものを削除する
- daemon は、target の prefix を見分けない(`process:` を含む。付け替えは、target の文字列の一致と `pid` だけで判定する)。
  `state.json` の読み込みの移行(`:` を含まない target に `iterm2:` を前置する)は、変更しない
- §3.4 の遷移(`transitions.rs`)は、変更しない(表は、上の順で決めたエントリの状態に適用する)
- 既存実装: `crates/shiibar-ccd/src/core.rs`(`find`、`handle_report`、`handle_reconcile`、prune、配信の条件)、`transitions.rs`、`state.rs`、
  `crates/shiibar-cc-proto/src/lib.rs`(`AgentRemoved` の reason、`ReconcileSession`)

### T8(アプリ): 未確認を下ろす操作、`rekey`、通知のクリック

- 仕様: DESIGN.md §4.5「未確認を下ろす操作」・「デスクトップ通知」の `rekey` と「通知のクリック」
- 利用者の操作で Running の行を選択した時点から計測し、その行の選択が DESIGN.md §9 の時間(1 秒)続いた時点で、行が未確認であれば `shiibar-cc seen <target>` を実行する。
  選択の時点では実行しない。計測を開始する操作: 行のクリック、↑ / ↓、選択なしの間の Enter による先頭の行の選択(検索欄と一覧)、詳細ページでの前後の会話への切り替え、通知のクリックによる選択。
  計測は、選択の時点で行が未確認かどうかに関係なく開始し、未確認かどうかは、時間が経過した時点で判定する。行のドラッグの開始は、Running の行には無い操作なので、対象に含めない
- 選択中の行に対する次の操作は、計測を最初から開始する: 選択が残るクリック(灰色で表示している選択中の行のクリック)、選択中の行のダブルクリック、
  主ボタンが disabled の Jump である行での Enter(どのページでも。1 列の詳細ページを含む)、ジャンプできないセッションの通知のクリック(その行が既に選択中の場合を含む)。
  青で表示している選択中の行の 1 回のクリックは、選択を解除するので、計測を中止する(クリックの時点で中止する。選択の解除は、ダブルクリックの間隔を待って確定する)。
  同じ行での 3 回目以降の連続のクリックは、計測を最初から開始する。ジャンプできる行の Enter は、Jump の成功で CLI が下ろす
- 計測を中止する: 選択が別の行に移動したとき、選択が外れたとき(選択の解除、選択中の行が一覧から無くなったとき)、ポップオーバーまたはウィンドウを閉じたとき。
  中止した後は、上の操作で最初から計測する。ウィンドウが key でなくなっただけでは、中止しない
- 利用者の操作によらない選択では、計測を開始しない: 閉じる前から保持している選択、選択を保持したまま行が Running に移った場合(Resume の後など)、`rekey` による選択の引き継ぎ。
  選択中の行が未確認になっただけでは、下ろさない。計測中に `rekey` を受信した場合は、計測を継続し、時間が経過した時点で、新しい target に `seen` を実行する
- 会話ペインの操作(クリック、キーの入力、スクロール)では、下ろさない
- グローバルホットキーで開いたときに、行を選択しない(DESIGN.md §4.5「グローバルホットキー」): 一覧にフォーカスを移し、選択は変更しない。行が 1 つも無い場合に検索欄にフォーカスを移す動作と、
  詳細ページを表示している場合の動作は、変更しない。一覧にフォーカスがあり選択なしの間の Enter は、検索欄の Enter と同じく、先頭の行を選択する(行が 1 つも無いときは何もしない。⌘Enter は何もしない)
- 計測は、時計とタイマーを注入できる形にして、テストで実際の時間を待たない
- `rekey` の後の再送: `seen` の subprocess の開始から終了までの間に、その target の `rekey` を受信した場合に限り、subprocess の終了の後に、`to` のエントリが未確認であれば、
  `to` に `seen` を 1 回だけ再送する。この期間の外の `rekey` では、再送しない。
  `Mark all as read` の `seen` も、同じ経路で実行し(対象の行ごとの `seen` を、並行して実行する)、再送の対象である
- 「計測を開始するか、中止するか」の判定(選択の種類と操作から決める)と、時間が経過した時点で「下ろすかどうか」の判定(行の状態から決める)は、Core の純関数にして、テストする。`seen` の実行は、既存の `Mark all as read` と同じ経路(CLI の subprocess)を使用する
- `rekey`: reason が `rekey` の `agent_removed`(`to` が新しい target)は、削除ではなく、付け替えとして扱う。発火済みの記録、発火を待っている遅延通知、行の選択、
  会話ペインの表示を、`to` の target に引き継ぐ(待っている遅延通知は、`to` の target の最新の状態で再確認し、`to` の target の通知として配信する)。配信済みの通知は消さず、古い target と `to` の対応を記憶する(アプリの終了で破棄する)。対応は連続して辿り、辿る回数は、記憶している対応の件数を上限にする。
  最新の付け替えの `to` は、読み替えの終端にする(対応を記憶するときに、`to` を古い target とする対応を先に破棄する。対応は循環しない)。
  snapshot と `status_changed` に含まれる target は、古い target としての対応から外す。古い target と `to` が同じ `rekey` では、何も変更しない。
  エントリの配信済みの通知を消すとき(focus、未確認が下りたとき)は、そのエントリの以前の target で配信した通知も消す。
  付け替えの前後で、通知が新しく発生しないこと、行の選択が外れないことを確認する
- 通知のクリック: 通知が持つ target を、付け替えの対応があれば新しい target に読み替えてから、分岐する。ジャンプできる target は、既存の focus。
  ジャンプできない target は、DESIGN.md の順(画面を開く、通常の一覧に戻す、Running の区画を開く、検索文字列を消去する、1 列の詳細ページでほかの会話を表示している場合は一覧のページに戻る、
  行を選択する(選択中の場合は解除しない)、未確認を下ろす計測を開始する(選択が変化しない場合も、最初から)、スクロールする、キーのフォーカスを一覧に移す)で実行する。1 列で、詳細ページを新しく開かない。エントリが無い場合は、画面を開くだけにする。
  検索の結果を表示している間のクリックでは、検索文字列の消去と同時に、Running の区画の絞り込みを解除する(次の一覧の結果を待たずに、その行を表示して選択する)。
  消去の時点で、実行中の search を中止し、クリックより前に開始した検索の結果は、後から届いても反映しない。
  行を選択する時点: ポップオーバーの形と、開いているウィンドウでは、画面を開いた直後。ウィンドウの形で、閉じているウィンドウを開いた場合は、ウィンドウが key になった時点
  (グローバルホットキーと同じ DESIGN.md §9 の時間の中)。その時間の中で key にならなかった場合は、時間が経過した時点で選択する(ホットキーの場合は、フォーカスを移さないまま)

### T11(アプリ): バージョンが異なる daemon にアタッチしない

- 仕様: DESIGN.md §4.5「daemon のライフサイクル管理」・§4.2「プロトコル契約」
- アタッチの時点(起動時と、再接続の時点)で、応答した daemon に `info` を送り、`version` を、アプリのバンドルのバージョン(`CFBundleShortVersionString`)と比較する(どちらも、末尾の `-dev` を除く)。
  異なるときは、その daemon に `shutdown` を送り、daemon が停止した後に、同梱の `shiibar-ccd` を spawn する。同じときは、そのままアタッチする。
  `info` が失敗したときは、アタッチする
- 「停止した」は、socket のファイルが無くなった、または socket への接続が拒否される状態である(それ以外の接続のエラーは、停止していないと判定する)。`shutdown` の送信から DESIGN.md §9 の時間(3 秒)まで、0.1 秒の間隔で確認し、
  停止しなかったときは、spawn せず、切断の状態のままにして、既存の切断の警告行を表示する。時間の待ちは、注入できる形にする
- 停止しなかった入れ替えは、保留にする。その後のアタッチのたびに(このアプリが spawn した daemon が実行中である場合を除く)、daemon が停止しているときは、
  同梱の `shiibar-ccd` を 1 回 spawn して、アタッチする(保留は終了する)。停止していないときは、`info` も `shutdown` も送らずにアタッチし、保留を継続する。
  停止を確認できない間は、spawn しない。`shutdown` を送るのは、1 回の起動につき 1 回までである
- 入れ替えは、アプリの 1 回の起動につき 1 回だけ実行し(停止しなかった入れ替えも、1 回に数える)、このアプリが spawn した daemon
  (このアプリが spawn したプロセスが実行中である間の、応答した daemon)には実行しない。この条件で入れ替えないときは、バージョンが異なっても、アタッチする
  (バージョンが異なる 2 つのアプリが、同じ state dir で同時に起動している場合も、それぞれ 1 回で止まる)
- アプリのバンドルのバージョンを取得できない場合、または同梱の `shiibar-ccd` が無い場合(バンドルにしないで実行したアプリ)は、比較せずにアタッチする
  (`docs/DEVELOPMENT.md` の、手動で起動した daemon との併用を維持する)
- 既存の spawn の条件(`DaemonLifecycleManager.swift` の、最初の接続の失敗のときだけ spawn する条件)は、入れ替えの後の spawn を実行できるように拡張する
- 比較の判定(2 つのバージョンの文字列から、入れ替えるかどうかを返す)は、Core の純関数にして、テストする。`info` の送信、`shutdown` の送信、spawn は、注入できる形にする
- `scripts/dev-install.sh` は、インストールの前にアプリと daemon を停止するので、変更しない。`scripts/dev-reload.sh` は、インストール済みのバンドルの 3 つのバイナリだけを差し替え、
  バンドルのバージョン(`Info.plist`)を書き換えない。ワークスペースのバージョンを変更した後は、バンドルのバージョンと同梱の daemon のバージョンが一致しない場合があるが、
  上の 2 つの条件(1 回の起動につき 1 回、アプリが spawn した daemon を対象にしない)によって、終了と起動を繰り返さない。スクリプトは変更しない
- 既存実装: `ShiibarCcApp/DaemonLifecycleManager.swift`(アタッチ、spawn、`shutdown`)、`DaemonConnection.swift`、daemon の `info`(`crates/shiibar-ccd/src/core.rs`)

  10. Ghostty(1.4.0 以上)で Claude Code を起動すると、Running に行が表示され、Jump で、その端末が前面に表示される(別のウィンドウ、別のタブ、分割、別の Space。

  11. Settings の General に `Terminal` の行がある。最初の値は、最後に使用した対応ターミナルを記録していたバージョンから更新した場合は、そのターミナルであり、
      それ以外の場合は、iTerm2 がインストールされていれば iTerm2、インストールされていなければ Terminal である。iTerm2、Terminal、Ghostty のそれぞれを選択して、
      Resume と Branch が、選択したターミナルの新しいウィンドウで実行される。別のターミナルのセッションを操作した後も、開く先が変化しない
  12. インストールしていないターミナルを選択すると、Settings に理由の 1 行が表示され、Resume と Branch が押せなくなり、ボタンの行の上に理由が表示される
  13. Setup Check に、Ghostty の許可の検査が表示される(Ghostty が起動している間)。iTerm2 だけを使用している場合に、Ghostty と Terminal.app の許可のダイアログが表示されない。

  15. hook の実行が、Claude Code の操作の遅れとして感じられない(対応ターミナルと、それ以外の両方。daemon を終了した状態を含む)
